# Ember Attractor — Black Hole

A one-room Unreal Engine **5.7.4** / C++ / Niagara game for *Niagara at Scale*. An explosion scatters hot matter; the player steers a black hole that swallows it. Every particle that crosses the event horizon is read back from Niagara into C++, its remaining heat becomes mass, and the mass makes the horizon and the pull bigger. Reach critical mass before the matter cools.

The direction comes from the gravity effects in our *Gravity* project (explosion debris and a black hole), rebuilt independently here: no Gravity assets or code are used.

## The game

| | |
|---|---|
| **Goal** | Reach critical mass (default 35) before the 40-second timer ends. |
| **Move** | The black hole follows the mouse on the chamber plane. Matter it touches is swallowed for free. |
| **Pull** (hold left mouse) | Draws matter in from the pull radius and spins it into an accretion swirl. Pulling drains **energy** (30/s); releasing recharges it (14/s). An empty tank locks the pull until it recharges to 25. |
| **Cooling** | Matter is worth full value when released and loses value linearly over 35 s (its colour fades from hot to cold). Cold matter still gets swallowed but adds nothing. |
| **Growth** | Mass enlarges the event horizon (45 cm + 3.5 cm per mass) and strengthens the pull (×2 at 30 mass). |

The tension is the energy budget against the clock: pulling gathers matter faster but runs dry, while waiting lets the matter cool. All released matter is worth 100 mass when hot (60 GPU dust + 40 CPU debris in mode 3), spread over the particle count, so a round plays the same at every count preset.

Reference games: **PixelJunk Shooter** (simulated material as the puzzle) and **Noita** (hot material whose state matters).

## Two systems at opposite ends of the cost curve

| | System 1: `NS_Embers_GPU` (dust) | System 2: `NS_Debris_CPU` (debris) |
|---|---|---|
| Simulation | GPU compute | CPU (VM) |
| Renderer | Sprites | Static meshes |
| Default / sweep counts | 100,000 / 100k–8M | 500 / 500–20k |
| Per-particle rules | Spring pull to the hole, vortex swirl, drag | Same, plus scene collision against the floor |
| State | Age-driven heat and colour | Age-driven heat and colour, collision response |
| To gameplay | Event-horizon export (GPU readback) | Event-horizon export (synchronous) |

Both systems are generated by `Source/EmberAttractorEditor/BuildEmberLabCommandlet.cpp`, so every module and binding is reviewable as code.

## Two-way data path

**Gameplay → Niagara** (user parameters, set every tick in `AEmberLabActor::Tick`): `User.AttractorPosition`, `User.AttractionStrength` (0 when not pulling), `User.PullRadius`, `User.VortexStrength`, `User.HorizonRadius`, `User.CoolSeconds`, `User.ParticleCount`, and `User.ExportHandler` (the actor itself).

**Niagara → gameplay** (event-horizon export, particle update stack):

1. `Export Particle Data` writes a particle when `distance(Particles.Position, User.AttractorPosition) < User.HorizonRadius`, sending `Particles.Age` in the Size slot.
2. `Kill Particles` kills exactly the particles the export reported in that frame (it reads the export module's `DataWasExportedThisFrame` output), so each particle is reported once.
3. `AEmberLabActor::ReceiveParticleData_Implementation` receives the batch (CPU: same frame; GPU: after asynchronous readback, a few frames later) and adds `share / count × heat` to the mass.

The GPU export reserves 16,384 entries per frame. Writes past that would be dropped, so the HUD and log report any frame that fills it (`full readbacks`); none occurred in testing. In a 100,000 + 500 test round the callback reported exactly 100,000 GPU and 500 CPU particles: no losses or duplicates.

## Build and run

Prerequisites: Windows, Unreal Engine **5.7** (tested 5.7.4), Visual Studio 2022 with the C++ game workload, Git.

```powershell
git clone https://github.com/TakayaEnomoto/EmberAttractor.git
cd EmberAttractor
powershell -NoProfile -File .\Tools\Build.ps1
```

`Tools/Engine.ps1` finds UE 5.7 from the Epic launcher manifest or the registry; otherwise set `$env:UE57_ROOT`. Then double-click `Play_Lab.cmd` (standalone 1080p) or `Open_Editor.cmd` and press Play. Click the viewport once so it receives input. The Niagara assets and map are committed, so a fresh clone does not need to regenerate them.

To regenerate the assets from code (overwrites `Content/EmberLab`): close the editor, run `Tools/Build.ps1`, then `Tools/BuildAssets.ps1`. The generator writes `Saved/AssetBuildReport.txt` and the translated particle-update HLSL (`Saved/Hlsl_*.hlsl`) for review.

|---|---:|---|
| `ember.Mode` | 3 | 0 none, 1 GPU only, 2 CPU only, 3 both |

| `ember.CPUCount` | 500 | CPU burst count, 0–100,000 (restarts the round) |

| `ember.TargetMass` | 35 | Critical mass to win (of 100 available when hot) |
| `ember.CoolSeconds` | 35 | Seconds for matter to cool to zero value |
| `ember.AttractionStrength` | 4 | Base pull stiffness (1/s²) inside the pull radius |
| `ember.CPUDynamicBounds` | 0 | 1 swaps the CPU system for the dynamic-bounds variant (bounds optimization "before" case) |
| `ember.DebrisOnGPU` | 0 | 1 swaps the debris for the same emitter simulated on the GPU (CPU-to-GPU port comparison) |

Count presets: GPU 10k, 25k, 50k, 100k, 200k; CPU 500, 1k, 2k, 3.5k, 5k. Useful stats: `stat Niagara`, `stat GPU`, `fx.Niagara.Debug.Hud Enabled=1 OverviewEnabled=1`.

## Performance evidence

Budget, stated before building: **60 fps (16.6 ms) at 1080p, with Niagara at most 4 ms combined game and render thread**; GPU time is recorded separately.

- `Tools/Capture.ps1 -Mode 1 -GPUCount 1000000 -Seconds 20` captures one configuration in the lab sandbox at 1080p: moving attractor, Unreal Insights trace (omit with `-NoTrace`), engine CSV with per-system Niagara stats, frame-time CSV, `stat Niagara` / `stat GPU` / Niagara Debugger overlays, and a screenshot. `-DynamicBounds` and `-DebrisOnGPU` select the optimization variants.
- `Tools/Sweep.ps1` runs the whole scaling sweep (baseline, 8 GPU counts, 6 CPU counts, 2 dynamic-bounds runs, 4 GPU-port runs) without traces, one fresh game per level (about 10 minutes).
- `python Tools/SummarizeSweep.py` freezes the CSVs (engine CSVs gzip-compressed) and logs into `Evidence/Final` with checksums and writes `Documentation/Sweep.md` and `Documentation/SweepChart.svg`; `python Tools/MakeReport.py` renders the report from them with local Edge/Chrome.
- `Tools/RecordDemo.ps1 -Monitor 1 -FFmpeg <ffmpeg.exe>` records the scripted showcase used for `Video/EmberAttractor_demo.mp4` (`-EmberDemo`: a winning round, a round where the matter goes cold, then `stat fps`/`stat unit`/Niagara Debugger while scaling to 4M GPU embers and comparing CPU debris with the GPU port). It centres the 1920×1080 client area on the chosen monitor and captures only that rectangle to `../Video/`.
- Unreal Insights traces (default game, GPU 8M, CPU 10k; 30–340 MB each) are too large for Git and stay in the ignored `Saved/Profiling` folder; regenerate them with `Tools/Capture.ps1` (without `-NoTrace`).

### Results at a glance (workstation above lab spec; see the report for method)

| | Passes budget up to | Fails at | Limiting factor |
|---|---|---|---|
| GPU sprites | 6,000,000 (P95 15.5 ms) | 8,000,000 (P95 25.8 ms) | GPU sprite rendering; Niagara CPU cost flat at ~0.13 ms |
| CPU meshes | 5,000 (P95 9.9 ms, Niagara 2.85 ms) | ~7,000 for the 4 ms Niagara budget; 10,000 for the frame (P95 20.4 ms) | Game thread: ~0.5 µs per particle plus scene-collision traces |

Optimizations measured on identical workloads: fixed vs dynamic bounds made no significant difference to Niagara cost (−2.9% at 20k). Porting the debris to GPU simulation cut Niagara GT+RT from 10.2 ms to 0.15 ms at 20k meshes (P95 38.1 → 5.0 ms), at the cost of analytical floor collision instead of scene traces, plus readback latency.

Results and interpretation: [Documentation/PerformanceReport.pdf](Documentation/PerformanceReport.pdf) (two pages; generated from `Documentation/PerformanceReport.html`). Week 1 evidence remains in `Evidence/Week1` and `Documentation/Week1_Status.md`.
