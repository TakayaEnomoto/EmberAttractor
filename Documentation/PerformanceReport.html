Ember Attractor — Performance Report

Niagara at Scale · UE 5.7.4 · Intel Core Ultra 7 265F, GeForce RTX 5070 Ti, 32 GB, Windows 11, D3D12, 1920×1080, VSync off

Budget and method

Budget (set before building): 60 fps, i.e. 16.6 ms per frame at 1080p, with Niagara at most 4 ms of combined game- and render-thread time. GPU time is reported separately.

Method: each count level is a fresh standalone game (Development editor build, -game, offscreen rendering) in the lab sandbox (ember.Game 0). That keeps the particle population constant while an automated attractor orbits and pulls. Each run has a 6 s warm-up and a 10 s capture, with stat Niagara, stat GPU and the Niagara Debugger HUD on. Frame time is wall-clock P95 from the game's own CSV, excluding three flagged screenshot frames. Niagara GT+RT is Particles/Total + Particles/RT per system from the engine CSV (fx.DetailedCSVStats). Unreal Insights traces were recorded separately for the default game and both breaking points. The stat overlays themselves cost about 1.0 ms of game-thread time (DebugHUD) in every run. The CPU, bounds and port runs were re-captured after adding the debris state machine; the GPU dust emitter did not change, so its earlier runs stand. Numbers come from a strong workstation, not the lab machines.

Where each system breaks

GPU sprites break on rendering, not on Niagara. Niagara's CPU-side cost stays flat at 0.12–0.14 ms from 100k to 8M particles: the CPU only dispatches the simulation. The GPU simulation itself scales linearly at about 0.36 ms per million particles (2.9 ms at 8M). The rest of the GPU frame is translucent sprite rendering, which grows from 2.1 ms at 100k to 14.4 ms at 6M and 24.3 ms at 8M. 6M still passes (P95 15.5 ms) and 8M fails (P95 25.8 ms), so the budget breaks between 6M and 8M. The render thread is waiting on the GPU, which makes this a fill-rate and overdraw limit.

CPU meshes break on the game thread. Each debris particle runs scene collision and a latched state machine (Drifting → Captured → Swallowed, with hysteresis). The state is evaluated in the lab too, so its cost is in these numbers. Niagara's own stat grows by about 0.5 µs per particle (0.40 ms at 500, 2.53 ms at 5k, 5.28 ms at 10k), so the 4 ms Niagara budget is crossed at roughly 7.5k particles. The whole-frame budget fails at 10k (P95 19.6 ms). The engine CSV shows why the frame cost rises faster than the Niagara counter: at 10k the collision module's scene traces cost 5.9 ms (CoreSystems_Collision), plus 5.6 ms of async-trace bookkeeping. Most of that is outside the per-system Niagara stat.

Before → after: CPU-to-GPU port. The same debris emitter (meshes, the same forces, state machine, export and kill) simulated on the GPU, selected with ember.DebrisOnGPU 1. At 20k meshes, Niagara GT+RT falls from 9.97 ms to 0.13 ms and frame P95 from 40.3 ms to 4.1 ms. At 10k it falls from 5.28 to 0.13 ms (P95 19.6 → 4.1 ms), while the GPU simulation costs only 0.03–0.04 ms. The price: GPU collision cannot trace arbitrary scene geometry the way the CPU can. Scene-depth collision killed the whole population in testing, so the port collides analytically with the floor plane. That is correct for this flat chamber and wrong for any other level. Gameplay data also arrives a few frames later through readback, and per-particle state is no longer cheaply readable on the CPU.

Many simple vs few complex

At about the same 10 ms frame, the GPU system draws 4,000,000 sprites (10.7 ms mean) while the CPU system manages 5,000 meshes (7.7 ms mean): roughly 800× more particles. Per particle the CPU path costs about 0.5 µs of game-thread time (plus scene traces); the GPU path costs about 0.36 ns of GPU simulation plus rendering. For a lead engineer: use GPU simulation whenever gameplay only needs an aggregate answer that can arrive a few frames late (how much matter crossed the horizon). Keep CPU simulation for the few particles that need exact same-frame state, arbitrary-geometry collision, or per-particle events that drive logic. This game does both: the dust is the GPU many, the debris the CPU few, and both feed the same readback path.

Gameplay readback

Getting data off the GPU is solved with an event-driven export, not a full readback. A particle is written to the Export Particle Data interface only in the frame it crosses the event horizon, and a Kill Particles module reads that same export flag, so each particle is reported exactly once. A 100,000 + 500 test round reported exactly 100,000 GPU and 500 CPU particles. The GPU reserves 16,384 entries per frame. A 4M-particle round swallowed 2.04M particles, at a peak of about 210,000 particles per second, without ever filling that reservation. The batch carries each particle's age, which becomes heat and then mass. Mass sets the horizon radius, pull strength, pull radius and vortex, which go back into Niagara as user parameters: a closed two-way loop. GPU readback latency (a few frames) was not measured precisely.

With another week

Measure readback latency per frame in Insights and run the sweep on the lab machines. Cut sprite overdraw, which is the GPU limit: smaller or opaque sprites, plus an Effect Type with distance and budget scaling. Fix scene-depth collision for the GPU port so it works beyond a flat floor. Add neighbor-grid queries so captured debris clump into larger, heavier chunks, giving the few-complex system more to do in play. Then play-test the energy and cooling numbers with other people.
